# 研究者交叉质询 v1

本文同步自 ReadLess 宿主开发记录；独立仓库验证见 [更新记录](UPDATE-2026-11-12.md)。

2026-11-12。实现用户确认的两处协作：第一轮资料阅读后的相互质询，以及正式回答核验后的定向追问。它们复用已有 Researcher 任务身份、冻结证据和运行账本，不是无边界的全员聊天室。

## 流程位置

开启新运行配置 `peer_review_workflow_version: 1`，且采用 adaptive/source-first 流程时：

```text
规划 → 并行研究子任务 → join → merge
    → peer_consultation（最多两轮）
    → gaps → 必要时进入已有的一批补充研究 → 写作
    → 整篇核验 → 核验者向相关研究者追问 → 编辑／完整复核 → 交付
```

旧运行快照没有开关时仍走原流程，不注入协商上下文提示。当前适配器版本为 52，默认模型及 high 推理设置保持。第一轮只有一个研究任务或没有可用原文片段时，写作前的相互质询会跳过；单任务仍可参与写作后的定向追问。

## 写作前的两轮讨论

- 当前选取最多前三个初始研究任务参与，保留其任务 ID、研究范围、排除项、原有验收问题和实际已读来源。没有增加新的研究维度。
- 每位参与者以自己的任务身份调用 `peer_questioner`，可自主选择另一位参与者，提出一条澄清、证据冲突或缺失证据问题，也可以不提问。
- 每轮最多接受两条问题，第二轮轮换提问顺序；总共最多两轮。后续问题可以绑定此前自己参与的问答，继续追问。没有有价值的问题时提前结束。
- 问题必须关联已存在的 criterion。事实澄清需引用已提供的原文片段；声称冲突至少引用两个片段。缺失证据问题可以没有引用。伪造的任务、criterion、片段或前序问题 ID 会被拒绝。
- 接收者通过 `peer_responder` 回应，输出 `clarified`、`needs_research` 或 `unresolved`。`clarified` 必须引用实际提供的原文；它表示研究者报告已澄清，**不等于事实核验通过**。

讨论不执行网页搜索，也不能直接创建任意工具任务。源内容、同伴消息和读书笔记均作为不可信材料，不能成为覆盖用户要求的指令。

## 资料与引用校验

讨论使用已有来源笔记的冻结原文。进入快照前检查来源哈希、source ID、字符范围与原文逐字一致性。每个快照最多选入 12 个完整片段，按来源交错选择；写作后优先选入被质疑段落引用的来源。每次模型调用还按运行快照的输入上限裁剪完整片段，并记录遗漏数量，不截断原文后冒充完整证据。

每个片段的讨论别名仅在其快照中有效。送给写作／编辑／核验阶段的讨论摘要保留原 source ID 和字符位置，不把讨论别名当成答案的引用 ID；答案仍只能引用当前材料包提供的正式片段。

## 协商如何进入补查

尚未解决的问题会合并到现有 `gaps` 中，不提升任何已覆盖比例，不把研究者的一致意见写成已验证 claim。原问题是否必需、所属维度和排除项保留，重复 criterion 的问题合并。

主流程仍只允许原有的一批、最多两个补充任务。补查继承接收者原任务的排除项、观察到的来源地址及安全搜索词，并携带具体质询问题和来源 ID。私有／混合场景沿用改写阶段冻结的公开查询词；讨论中的私有内容不被转成公开搜索词。

补查会先针对相关冻结原文重新阅读。此前的“资料已充分”判断不能让这一步直接跳过。具体问题进入新的阅读缓存键和 source-reader 输入，避免只回放此前未考虑该问题的阅读结果；上下文从子图检查点恢复，即使重启后直接进入阅读节点也不丢失。

有可重读证据的质询补查无需预留新的网页搜索次数，但仍服从研究时间和 token 预算。资料是否足够，仍由原有材料判断和最终独立核验决定。补查后不会凭讨论记录自动宣布所有争议已解决。

## 写作后的定向追问

整篇核验发现事实问题或不受支持的重要事实时，最多向研究者发起两次追问。优先按段落引用的来源寻找原阅读者，其次按原任务问题匹配；这一阶段可在全部初始任务中选择接收者。

追问包含被质疑的正文、核验问题和原文资料。回应作为编辑输入，但不会删除核验意见、把 unsupported 改成 supported，或替代原有的补查、完整编辑和整篇复核。核验已通过的回答不额外启动这段讨论。

## 恢复、限额与失败处理

| 约束 | 当前默认值 |
| --- | --- |
| 写作前讨论 | 最多 2 轮、每轮 2 条问题、最多 3 名任务参与者 |
| 写作后追问 | 最多 2 条 |
| 讨论模型调用 token 子限额 | 48,000，包含于原总预算及相应阶段预算中 |
| 讨论 HTTP 尝试子限额 | 16 次，包含重试与结构修正 |
| 新讨论调用的时间余量 | 至少 45 秒；已保存的模型结果可回放 |

新限额使用原操作账本的事务预留、实际用量结算和未知成本保守记账。没有增加整体 token／搜索／抓取上限。讨论阶段 token 子限额只统计两个 peer 角色；由讨论触发的正式补查仍计入原研究预算。

快照、裁剪后的输入、模型返回、逐条问答和阶段结果都持久化。恢复时回放已保存结果，不重复购买已完成调用。部分回应失败时记录为 unresolved；讨论时间或预算不足会标为 partial，主流程可继续使用已有材料写作。取消和致命错误继续向上传递，不伪造已完成的协作。

## 可观察记录

前端进度增加“研究者交叉核对”，保持现有聊天布局。通过现有鉴权、按运行隔离的 `/v1/research/{run_id}/events` 可查看：

- `researcher.exchange`：提问者、接收者、问题、回应、原文位置和来源哈希。
- `researcher.consultation_finished`：阶段、状态、问题数量、未解决数量和停止原因。

运行预算同时保存 `tokens_peer_review` 和 `peer_review_http_attempts`。没有把内部讨论自动发布为独立用户聊天，也没有将它写入长期事实记忆。
